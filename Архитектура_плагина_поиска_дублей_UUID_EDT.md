# Плагин «Поиск дубликатов UUID элементов конфигурации» для 1С:EDT 2025.x / 2026.x — архитектура решения

Документ описывает архитектуру Eclipse-плагина для 1С:EDT (RCP на базе Eclipse Equinox, Java 17), который находит дубликаты UUID элементов конфигурации в открытом проекте EDT, сканируя системные XML-файлы метаданных (`.mdo`), и сообщает о них разработчику через стандартные механизмы Eclipse (маркеры в Problems view + собственная view).

---

## 1. Что это за плагин с точки зрения платформы

1С:EDT — это Eclipse RCP-приложение (OSGi/Equinox). Поэтому плагин — обычный Eclipse-плагин (OSGi-бандл + `plugin.xml`), использующий стандартные Eclipse API для работы с ресурсами, маркерами и UI. Для данной задачи специфичные внутренние API 1С (модель конфигурации `com._1c.*`, компилятор) не требуются: работа идёт на уровне файловой системы проекта.

Проект 1С:EDT для прикладного кода хранится в дереве каталогов: в корне проекта каталог `src`, внутри — файлы метаданных `.mdo` (XML, где и лежит атрибут `uuid`), модули `.bsl` и служебные файлы. UUID элемента — атрибут `uuid` у элемента `.mdo`-файла. Дубликат — один и тот же `uuid` в двух и более разных файлах.

## 2. Общая схема (компоненты и потоки данных)

```
                    [ EDT (Eclipse RCP) ]

  [ Триггеры ]                     [ UI (Отчётность) ]
  • IResourceChangeListener        • Маркеры → Problems view
  • Проектный builder              • View «Дубли UUID»
  • Пользовательская команда       • Диалог-предупреждение
              │                             ▲
              ▼                             │
          [ UuidIndexService (общий сервис) ]
   Map< uuid, List<UuidOccurrence> >
   UuidOccurrence = { файл, тип элемента, строка }
              ▲
              │
          [ MdoUuidScanner (StAX/потоковый парсер) ]
   читает .mdo, извлекает uuid элементов
```

Три независимых потока:

1. **Сканирование** — парсер `.mdo` возвращает набор `(uuid, файл, строка, тип элемента)`.
2. **Индексация** — сервис поддерживает актуальную карту `uuid → вхождения`; умеет добавить, убрать и пересканировать файл.
3. **Отчётность** — на основе расхождений индекса создаёт/удаляет маркеры и обновляет view.

## 4. Сканер `.mdo` (парсер)

- **Технология — StAX (`XMLStreamReader`)**, потоковая обработка, а не DOM (не вычитывать файл целиком) и не regex (хрупко).
- У каждого XML-элемента с атрибутом `uuid` берём этот атрибут как собственный идентификатор.
- **Важно:** определяем только собственные `uuid` (атрибут `uuid`), а не атрибуты-ссылки (`ref`, `main`, `content` и т.п.), иначе будут ложные дубли.
- Выход на файл: `List<UuidOccurrence>`, где `UuidOccurrence = { String uuid; String elementType; int line; }` (строка из `location` парсера).
- Обработка ошибок: невалидный XML не роняет скан — пропускаем файл и фиксируем предупреждение.

---

## 5. Индекс (`UuidIndexService`)

Единая точка доступа для сканера, билдера и UI. Потокобезопасное хранилище:

- `Map<String, List<UuidOccurrence>> uuidToOccurrences` + обратная карта `file → Set<uuid>` для быстрого удаления файла.
- API: `rescanProject(IProject)`, `addFile(IResource)`, `removeFile(IResource)`, `changedFile(IResource)`, `checkAndReport(IProject)`.
- Совместимость: классы в одном бандле с парсером. Для разделения `core`/`ui` — публиковать как OSGi-сервис или статический синглтон.
- Индексация происходит в фоновых потоках; доступ из UI защищается синхронизацией.

## 6. Триггеры сканирования

### (A) Resource change listener — быстрая реакция на изменения в области проекта

- Регистрация `IResourceChangeListener` в `activate()`; события `POST_CHANGE`, обработка `IResourceDelta`.
- Файл добавлен/изменён/удалён/переименован → `addFile` / `changedFile` / `removeFile` / обновить оба пути при `MOVED_FROM`.

### (B) Проектный builder — полная контрольная пересборка

- Точка расширения `org.eclipse.core.resources.builders` + project natures.
- `fullBuild()` → `rescanProject`; `incrementalBuild()` → точечное обновление по дельте.

### (C) Пользовательская команда `CheckUuidCommandHandler`

Кнопка «Проверить дубликаты UUID» в контекстном меню проекта:

- Полный `rescanProject` + мгновенный отчёт; ручной запуск и способ тестирования.

**Рекомендация:** реализовать (A) + (C) обязательно, (B) — как желательный уровень надёжности (прогрев при `PROJECT_OPENED` также через (A)).

## 7. Отчёт разработчику (маркеры + view)

### Основная механика — маркеры `IResource`

- В `plugin.xml` заводится тип маркера `org.eclipse.core.resources.markers` с супертипами `org.eclipse.core.resources.problemmarker` и `textmarker`, severity `ERROR` (или `WARNING`), иконка.
- На каждое вхождение дубля — отдельный маркер на файле `.mdo` с атрибутами `LINE_NUMBER` и `MESSAGE`: «Дубликат UUID 7c…: тот же UUID уже используется в Configuration/.../X.mdo», `duplicateOf=...`.
- При исчезновении дубля — удаление маркеров.
- Маркеры автоматически появляются в **Problems view**; клик ведёт к строке `.mdo`; работает Quick Fix-инфраструктура.
- Рекомендация: `persistent = false` (временные маркеры одной сессии), чтобы не подчищать вручную при перескане.

### Дополнительная механика — собственная view `DuplicateUuidView`

- Таблица: `UUID | Кол-во вхождений | Список файлов (полные пути, строки)`.
- Строки с `count > 1`; двойной клик открывает файл на строке (`IDE.openEditor`).
- Совместно с маркерами в Problems даёт полную картину.

### Опционально

- Всплывающий диалог при первом обнаружении в сессии с настраиваемым флагом «показывать диалог».

## 8. Детекция дублей и жизненный цикл обновления

- Дубль = `uuid` в ≥2 разных `.mdo`-файлах (или дважды в одном файле — учитывать).
- Исключения: не трогать служебные каталоги (`.git`, `out`, `build`, `_src` дубли).
- Инкрементальное обновление: файл `X` изменился → `removeFile(X)` + `addFile(X)` → пересчитать затронутые `uuid` → обновить маркеры. Полный перерасчёт (сборка/команда): очистить маркеры проекта и собрать заново.

## 10. Производительность

- `.mdo`-файлов в большой конфигурации — тысячи; StAX-парсинг — миллисекунды на файл; полный скан — доли секунды–несколько секунд.
- Всё держим в памяти; `.bsl` не читаем (нужны только `.mdo`).
- Сканы — вне UI-потока (`WorkspaceJob` / билдер).

## 11. Развёртывание и разработка

- Среда: **Eclipse for RCP/Plug-in Developers**, target platform указывается на каталог установленной 1С:EDT 2025/2026.
- Java — та же версия, что у EDT (17).
- Зависимости MANIFEST: `org.eclipse.core.resources`, `org.eclipse.core.runtime`, `org.eclipse.ui`, `org.eclipse.ui.ide`.
- Сборка: PDE-экспорт бандла; установка — копия jar в каталог `dropins`/`plugins` EDT или через p2.
- Отладка: **Run As → Eclipse Application** с target platform = EDT; тестирование — отдельное рабочее пространство с копией проекта.

## 12. Риски и открытые вопросы

1. **Точный формат `.mdo`** — нужно подтвердить на живой копии проекта, где именно атрибут `uuid` (корневой тег и вложенные), есть ли ссылки с тем же именем атрибута.
2. **Структура проекта EDT** — подтвердить наличие каталога `src` и критерий «файл конфигурации», чтобы не сканировать лишнее.
3. **Разновидность проекта** (каталог `.mdo` vs `.mcf`/`.dt`) — для `.mcf`/`.dt` нужен другой адаптер, т.к. это не файловая область.
4. **Если нужны точные типы элементов из модели EDT** — придётся подключить `com._1c.*` API, резко усложняя совместимость между 2025/2026 (в текущей схеме не требуется).

---

## 13. Итог

Минимальный путь к рабочему прототипу: сканер на StAX → индекс-сервис → resource listener + команда → маркеры в Problems. Затем — view для удобной навигации, при необходимости builder и persistent-маркеры.
